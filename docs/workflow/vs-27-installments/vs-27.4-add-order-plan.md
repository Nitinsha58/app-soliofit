# VS-27.4 — Add Order Strict Plan

**Program:** [VS-27 overview](./00-overview.md) · **ADR:** [ADR-0009](../../adr/ADR-0009-strict-installment-plan.md)
**Layer:** Frontend (Add Order flow) · **Depends on:** 27.1, 27.3 · **Status:** Pending

Bring the Add Order billing step onto the strict, atomic model: a default installment is
pre-seeded from the bill, splitting must balance, and the whole order + schedule is created
in a single atomic call.

> **Frontend Design Gate:** read `07-ux-guidelines.md § 0` before editing this UI and run
> the § 0 pre-build checklist.

---

## Goal

- Show the user a **default installment** (= bill, due delivery date) the moment a bill is
  entered — the mandatory-but-non-blocking default.
- Let them optionally split it; **block proceeding/creating unless `Σ == bill`.**
- Send the installments **inside** `createOrder()` so order + schedule are created atomically
  (no more post-create `Promise.allSettled` loop).

## Scope (in)

1. **`AddOrderFlow/index.tsx`**
   - Send `installments` as part of the `createOrder()` payload.
   - Remove the separate `Promise.allSettled` installment-creation loop.
   - Photos/voice remain fire-and-forget (not money; unchanged).
2. **`DraftInstallments.tsx`**
   - **Seed a default installment** when a bill is present: `amount = bill`,
     `due_date = deliveryDate`. Re-seed/clear sensibly when the bill changes.
   - **Strict balance gating:** the billing step's continue / the final Create is disabled
     unless `Σ(draft installments) == bill`. Show a clear, calm "Remaining ₹X" / "Over by
     ₹X" status (color = status only).
   - Use **`QuickDateInput`** (27.3) for due dates.
3. **`lib/api/orders.ts`** — `createOrder` accepts optional `installments[]`.
4. **`lib/api/installments.ts`** — (if not already in 27.1's contract surface) ensure the
   create types align; the drawer-only `replaceSchedule` lives in 27.5.

## Scope (out)

- No backend changes (consumes 27.1's atomic create + default behavior).
- The drawer editor is VS-27.5.

## Files

## Review (how to verify)

- Type-check via Docker: `docker compose -f docker-compose.dev.yml exec frontend npm run type-check`.
- Manual flow: enter a bill → default installment appears; try to create with `Σ != bill`
  → blocked with a clear status; split into two that sum to the bill → create succeeds and
  the order + both installments exist (one atomic call, verify in network tab).
- Confirm no orphaned order is possible if an installment is invalid (server rejects the
  whole create).
- Hand off to Nitin + automation testing tool.

## Done when

The billing step seeds the default, enforces balance, and creates order + schedule
atomically, with quick date entry.
