# VS-27.2 — Legacy Audit + Backfill

**Program:** [VS-27 overview](./00-overview.md) · **ADR:** [ADR-0009](../../adr/ADR-0009-strict-installment-plan.md)
**Layer:** Backend (data / management command) · **Depends on:** 27.1 · **Status:** Pending

The MVP is **live in production** with real orders created under the old (flexible) rules.
Many have no installments; some are partially scheduled. Under the strict invariant these
would show inconsistent payment state forever unless reconciled. This slice brings existing
data onto the invariant, safely and auditably.

---

## Goal

Reconcile every existing billed order so `total_amount == Σ(installments)` — without
touching paid history — and surface anything that needs a human decision.

## Approach — one idempotent management command

`backend/apps/payments/management/commands/backfill_installments.py`

- **Default mode = dry run.** Prints a full report and changes nothing.
- `--apply` performs the writes (each order inside its own `transaction.atomic()`).
- Idempotent: re-running after `--apply` reports "0 to change."

### Per-order classification (billed = `total_amount > 0`, not soft-deleted)

**Check `Σ(paid) > total_amount` FIRST** — an order that has already collected more than the
bill violates the ADR-0009 invariant `total_amount ≥ Σ(paid)` and can never be auto-balanced
(you cannot subtract paid money). It is always manual review, even when `Σ(all)` is also over
the bill. Only after that check do we classify by `Σ(all)` vs `total_amount`.

| Case | Condition | Action |
|------|-----------|--------|
| **Paid exceeds bill** | `Σ(paid) > total_amount` | **No auto-fix** — list in manual-review report, flagged explicitly as **"paid exceeds bill (₹paid vs ₹bill)"**. Highest priority; check before all others. |
| **Unscheduled** | no installments (and `Σ(paid) ≤ total`) | Create **one default unpaid installment**: `amount = total_amount`, `due_date = delivery_date`, `remarks = "Auto-balanced during VS-27 migration"` |
| **Partial** | `0 < Σ(all) < total_amount` | Add **one balancing unpaid installment**: `amount = total_amount − Σ(all)`, `due_date = delivery_date`, `remarks = "Auto-balanced during VS-27 migration"` |
| **Balanced** | `Σ(all) == total_amount` | No change |
| **Over-scheduled (scheduled, not paid)** | `Σ(paid) ≤ total < Σ(all)` | **No auto-fix** — manual-review report (auto-removing rows could touch paid ones) |
| **Unbilled** | `total_amount == 0` | No change |

- The `"Auto-balanced during VS-27 migration"` remark makes every generated row auditable
  and self-explanatory later.
- Paid installments are **never** modified; the balancing amount is computed against the
  sum of *all* existing rows (paid + unpaid), so paid amounts are respected.

### Report output (both modes)

- Counts per case (paid-exceeds-bill / unscheduled / partial / balanced / over-scheduled / unbilled).
- A line per order that will change (order_number, current Σ, total, action).
- A clearly separated **"Manual review required"** section listing both **paid-exceeds-bill**
  (with the `₹paid vs ₹bill` figures) and **over-scheduled** orders.

## Scope (out)

- No schema change. No changes to live endpoints (consumes 27.1's model rules only).
- No UI. The report is CLI output (optionally written to a file for the record).

## Tests (must cover)

- Unscheduled order → one default installment with the migration remark + delivery due date.
- Partial order → one balancing installment that makes `Σ == total`, paid rows untouched.
- Balanced / unbilled orders → unchanged.
- Over-scheduled (scheduled, not paid) order → reported, **not** modified.
- **Paid exceeds bill** (`Σ(paid) > total`) → reported in manual review with the figures,
  **not** modified — even when `Σ(all)` is also over the bill (paid-check takes precedence).
- Idempotency: second `--apply` run makes no changes.
- Dry run writes nothing.

## Review (how to verify)

- `docker compose -f docker-compose.dev.yml exec backend python manage.py backfill_installments`
  (dry run) → inspect the report.
- Re-run with `--apply` on a dev DB seeded with each case; confirm counts and that the
  payments dashboard now shows consistent state.
- Production run is a deliberate, logged operation: dry-run first, capture the report
  (especially the manual-review list), then `--apply`. Coordinate with Nitin.
- Hand off to Nitin; do not self-verify in browser.

## Done when

Dev DB reconciles cleanly and idempotently, the manual-review report is correct, and the
command is ready for a logged production run.
