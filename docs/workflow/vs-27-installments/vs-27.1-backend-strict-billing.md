# VS-27.1 — Backend Strict Billing Core

**Program:** [VS-27 overview](./00-overview.md) · **ADR:** [ADR-0009](../../adr/ADR-0009-strict-installment-plan.md)
**Layer:** Backend (`apps/orders`, `apps/payments`) · **Depends on:** — · **Status:** Pending

The foundation slice: it establishes and enforces the `bill = Σ installments` invariant on
every write path, so no other slice (or future caller) can leave billing inconsistent.

---

## Goal

- Create an order and its installments **atomically**, auto-seeding a default installment.
- Edit the bill amount and the unpaid schedule **together** in one transaction.
- Guarantee `total_amount == Σ(installments)` and `total_amount ≥ Σ(paid)` server-side.
- Remove the single-row write endpoints that could bypass the invariant.

> **Non-breaking by design.** 27.1 is purely **additive** — it adds new write paths and
> validates the invariant on *those paths only*. It does **not** remove or strict-validate
> the existing single-row endpoints, and it does **not** auto-default on create yet, because
> the current Add Order / drawer UI still uses the old flexible endpoints until 27.4 / 27.5
> ship. The breaking pieces land in a **cutover** (see below) bundled with the frontend
> release, so production is never left with a broken installment UI.

## Scope (in) — additive foundation

1. **Atomic order create with explicit installments**
   - `OrderSerializer` gains a **write-only, optional** `installments` field:
     `[{ amount, due_date, remarks? }]`.
   - In `OrderViewSet.perform_create` (inside the existing `transaction.atomic()` retry block):
     - If `installments` **provided** → validate `Σ amount == total_amount` (reject
       otherwise), then bulk-create them. Any failure rolls back the whole order.
     - If **omitted** → **current behavior, unchanged** (no installments created here). The
       auto-default-on-omit is deliberately deferred to the cutover (otherwise it would
       collide with the old Add Order UI, which still posts installments separately and would
       overshoot the bill).

2. **Combined atomic bill + plan edit — new endpoint (detail action on `OrderViewSet`)**
   - Implemented as `@action(detail=True, methods=['put'], url_path='billing')` on
     `OrderViewSet`, so it resolves to **`PUT /api/orders/{id}/billing/`**.
     ⚠️ It must **not** live under `apps.payments.urls` — that module is mounted at
     `/api/orders/<uuid:order_id>/installments/`, which would make the path
     `…/installments/billing/`. Order-scoped billing belongs on `OrderViewSet` / `apps.orders`.
   - **Request payload:**
     ```json
     {
       "total_amount": "10000.00",
       "installments": [
         { "amount": "4000.00", "due_date": "2026-06-20", "remarks": "" }
       ]
     }
     ```
     `installments` is the full set of **unpaid** rows the schedule should have after save.
   - **Validation (all server-side, atomic):**
     - `total_amount ≥ Σ(paid installments)` — else 400 "Bill cannot be less than the
       amount already paid (₹X)."
     - `Σ(paid) + Σ(payload installments) == total_amount` — else 400 "Installments must
       sum to the bill (off by ₹X)."
   - **Effect:** `select_for_update()` the order row, then update `total_amount`; **delete
     existing unpaid installments**; recreate from payload; **paid installments untouched** —
     all in one `transaction.atomic()`.
   - Writes an order activity (e.g. `BILLING_UPDATED` or reuse `PAYMENT_UPDATED`) capturing
     new total + installment count.

3. **Old single-row endpoints stay functional, marked deprecated.** `POST` (single),
   `PATCH`, `DELETE` remain as-is for the interim so the current UI keeps working; add a
   deprecation note in code. `GET` (list) and `mark-paid` retained. **No removal in 27.1.**

4. **Concurrency — lock the parent order on `mark-paid`.** `InstallmentMarkPaidView` must
   `select_for_update()` the **parent order** inside its transaction before setting
   `paid_date`. Locking only the installment row (as today) does **not** serialize a
   `mark-paid` against a concurrent `PUT …/billing/` replace — the order row is the shared
   serialization point, so both write paths must lock it. Without this, billing could
   validate against a stale `Σ(paid)` or delete a row being marked paid.

## Cutover (ships in the SAME release as 27.4 + 27.5)

These are the breaking changes; they land only when the frontend no longer needs the old
paths, so there is no broken-UI window:

- **Enable auto-default-on-omit** in `perform_create`: when `installments` is omitted **and**
  `total_amount > 0`, create **one default installment** (`amount = total_amount`,
  `due_date = delivery_date`, unpaid). `total_amount == 0` → no installment.
- **Remove** the single-row write routes (`POST` single / `PATCH` / `DELETE`) from
  `apps.payments.urls`.
- **Make `total_amount` read-only** outside `PUT …/billing/` (tighten the existing
  `partial_update` guard so bill edits route through the combined endpoint only).

## Scope (out)

- No model field changes / migration (the `Installment` model is unchanged).
- No frontend changes (27.4 / 27.5 consume these endpoints).
- Legacy data reconciliation is VS-27.2.

## API contract summary

| Method | Path | Purpose | 27.1 | Cutover (with 27.4/27.5) |
|--------|------|---------|------|--------------------------|
| POST | `/api/orders/` | Create order (+ optional `installments[]`) | Atomic when `installments` provided; omit = unchanged | Omit + bill>0 → auto-default |
| GET | `/api/orders/{id}/installments/` | List schedule | Unchanged | Unchanged |
| PUT | `/api/orders/{id}/billing/` | Atomic bill + unpaid-plan replace (OrderViewSet action) | **New** | — |
| POST | `/api/orders/{id}/installments/{iid}/mark-paid/` | Mark one paid | Unchanged | Unchanged |
| POST/PATCH/DELETE single installment | `…/installments/[{iid}/]` | Old flexible writes | **Kept, deprecated** | **Removed** |

## Files

- `backend/apps/orders/serializers.py` — write-only `installments` field + `Σ == total` validation
- `backend/apps/orders/views.py` — atomic create; **`billing` detail action** on `OrderViewSet` (→ `/api/orders/{id}/billing/`); _(cutover: auto-default-on-omit + `total_amount` read-only guard)_
- `backend/apps/orders/services.py` — shared billing-update logic + activity helper
- `backend/apps/payments/views.py` — `InstallmentMarkPaidView`: `select_for_update()` the parent order before setting `paid_date`; mark `InstallmentDetailView` / single-create deprecated _(cutover: delete them)_
- `backend/apps/payments/urls.py` — _(cutover only: remove single-row write routes)_
- `backend/apps/orders/tests.py` / `backend/apps/payments/tests.py` — new tests

## Tests (must cover)

**27.1 (additive):**
- Atomic create with `installments`: an invalid installment rolls back the whole order.
- Create with `installments` where `Σ != bill` → 400, nothing persisted.
- Create with `installments` omitted → behaves exactly as today (no installments created).
- `PUT …/billing/` resolves at `/api/orders/{id}/billing/` (not under `…/installments/`).
- `PUT …/billing/` happy path: bill + unpaid replaced, paid rows preserved.
- `PUT …/billing/` rejects `total_amount < Σ(paid)`.
- `PUT …/billing/` rejects `Σ(paid) + Σ(new) != total_amount`.
- Old single-row write endpoints still work (interim) — not strict-validated yet.
- `mark-paid` takes the parent-order lock (serializes against a concurrent billing replace).
- Soft-deleted orders' installments stay excluded (scoping intact).

**Cutover (with 27.4/27.5):**
- Default installment auto-created when `installments` omitted and `bill > 0`; `bill == 0` → none.
- Removed single-row write endpoints return 404/405 (no longer routable).
- `total_amount` edits outside `PUT …/billing/` are rejected.

## Review (how to verify)

- Run backend test suite: `docker compose -f docker-compose.dev.yml exec backend python manage.py test apps.payments apps.orders`.
- `curl`/Postman the create + `PUT …/billing/` flows against the dev backend; confirm the
  three 400 cases and the atomic happy path.
- Confirm the single-row write routes are gone (request returns 404/405).
- Hand off to Nitin + automation testing tool; do not self-verify in browser.

## Done when

The new create-with-installments path and `PUT …/billing/` behave per the contract with all
27.1 tests passing, the old endpoints still work (deprecated), and ADR-0009 is `Accepted`.
The side-door removal + auto-default + bill read-only guard are verified later, at cutover.
