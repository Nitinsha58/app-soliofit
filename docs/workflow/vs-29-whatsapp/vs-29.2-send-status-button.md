# VS-29.2 — Frontend: Send-Status Button on Overview

**Program:** [VS-29 overview](./00-overview.md) · **Layer:** Frontend (Order Detail drawer) · **Status:** Pending
**ADR:** [ADR-0010](../../adr/ADR-0010-whatsapp-click-to-chat-messaging.md)
**Depends on:** VS-29.1 (`messages_sent` on the order detail serializer).

> **Frontend Design Gate:** read `07-ux-guidelines.md §0` and run §0.10 before editing this UI.

Add a WhatsApp "Send <status>" action on the Overview, directly **below** the stage-aware
`PrimaryAction`, that opens WhatsApp prefilled with the order's current-status message (plus
a payment line when outstanding) and reflects whether that status has already been sent.

## §0.10 pre-build checklist — all "yes"

- Main goal visible in 5s? ✅ sits under the primary action, in the action zone.
- One dominant action? ✅ primary (gold, filled) stays dominant; this is a lighter **outline** secondary (§0.7).
- Rare actions hidden? ✅ no new admin surface; Resend is a quiet inline affordance.
- Related things grouped? ✅ a single messaging action; no mixed concerns.
- Readable without editing? ✅ no inputs; opens an external draft.
- Colors only for meaning? ✅ green = WhatsApp/completed; "sent" reads as done (§0.8).
- Status without calculating? ✅ label states the status; "sent · <time>" is precomputed.
- Destructive separated? ✅ nothing destructive.

## Scope (in)

1. **Templates module** `lib/whatsappTemplates.ts` — pure, swappable (the seam future
   in-panel template management replaces):
   - Status templates: `Booked`, `Started`, `Ready`, `Partial Delivery`, `Delivered`.
   - Payment block appended when outstanding: **full pending** (`payment_state: pending`,
     and `overdue` with nothing paid) and **partial — one paid, one pending**
     (`payment_state: partial`, and `overdue` with something paid). None for
     `completed`/`unbilled`.
   - Placeholders: customer name, order number, amounts (via existing `inr()`), shop name
     (auth store `business_name`, safe fallback), each tied to a `template_key`.
   - `buildMessage(order)` → `{ text, templateKey }` for the order's **current** status.
2. **Number normalization** — `91` + digits: strip non-digits; 10-digit → prefix `91`;
   existing 12-digit `91…` → as-is. Country code is a single constant. (ADR-0010 §2.)
3. **Component** `OrderDetailDrawer/WhatsAppAction.tsx`, rendered in `OverviewTab` right
   below `<PrimaryAction>`. Same width/radius as the primary; **secondary outline** weight.
   Three states (color = status, §0.8):
   - **Unsent** (no `messages_sent[order.status]`): green-outline, white bg, WhatsApp icon,
     `Send <Status>`. Tap → open `https://wa.me/<intl>?text=<encoded>` (new tab) **and**
     `POST /orders/{id}/messages/` `{order_status, channel:'whatsapp', template_key}`;
     optimistically set local `messages_sent[status]` so it restyles immediately.
   - **Sent** (`messages_sent[order.status]` present): muted/check style,
     `<Status> sent · <time>` (`lastChanged()` for the stamp) + a quiet **Resend** that
     repeats the open+POST.
   - **No phone**: disabled/greyed.
   - Always visible — including the Delivered terminal state where `PrimaryAction` shows no button.
4. **Types/API** — add `messages_sent?: Record<Order['status'], string>` to the `Order`
   type (present on detail fetch); add `sendOrderMessage(id, payload)` to `lib/api/orders.ts`.

## Scope (out)

- No in-app message preview/confirm modal (the WhatsApp draft is the preview; ADR-0010 §5).
- No template editing UI (future program item). No board/card button (Overview only).
- No delivery/read receipts.

## Review (how to verify)

- Type-check: `docker compose -f docker-compose.dev.yml exec frontend npm run type-check`.
- Open a Ready order → green-outline `Send Ready`; tap → WhatsApp opens with the Ready
  template; button flips to `Ready sent · <time>` with Resend; reload keeps the sent state.
- Outstanding payment: message includes the correct full-pending vs partial line; paid/unbilled: no line.
- Each status (Booked/Started/Ready/Partial Delivery/Delivered) shows its own label/template;
  Delivered still shows the button though the primary is gone.
- Order with no phone → button disabled. Number opens with `91` prefix.
- Visual sweep 375/768/desktop — primary stays dominant; secondary never out-weighs it.
- Hand off to Nitin + automation testing tool.

## Done when

From Overview, one tap sends the correct current-status WhatsApp message (with the right
payment line), and the action shows a server-backed "sent" state with Resend.
