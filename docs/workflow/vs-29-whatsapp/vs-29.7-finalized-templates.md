# VS-29.7 — Finalized Template Copy (frontend)

**Program:** [VS-29 overview](./00-overview.md) · **Layer:** Frontend · **Status:** Pending
**Depends on:** 29.5 (vault spec). Ships independent of working hours (pickup uses a fallback until 29.8).

> **Frontend Design Gate:** read `07-ux-guidelines.md §0` and run §0.10 before editing this UI.

Rewrite the template module to the finalized warm "ji"-tone set with status-aware payment context.
All existing send surfaces (detail button, dashboard card footer, post-create modal) inherit the
new copy with no change to their own code.

## Scope (in)

1. **`lib/whatsappTemplates.ts` rewrite** to the §10 `order_status` set — **Booked, Started,
   Ready, Delivered** — multiline `Hi {customer} ji,` … `— {boutique_name}` structure, each with a
   stable `template_key` (`status_booked`, `status_started`, `status_ready`, `status_delivered`).
2. **`{item}` → "order"** everywhere for now (e.g. "Your order is ready!"). Single constant so the
   future structured-item field is a one-line swap.
3. **Status-aware `paymentContext(order)`** matching the §10 state table:
   - Booked: balance due → `Total: ₹{total} — ₹{paid} paid, ₹{remaining} balance.`; full advance →
     `Total: ₹{total}, paid in full. Thank you!`
   - Ready: fully paid / partial / full pending lines.
   - Delivered: balance remaining → open-balance line; fully paid → **omit**.
   - `unbilled` (total 0) → omit everywhere. Inserted only into Booked / Ready / Delivered.
4. **Partial Delivery — no messaging.** `buildMessage(order)` returns **`null`** when
   `order.status === 'Partial Delivery'` (no template for now; documented future revisit once the
   Partial Delivery model is fixed). All send surfaces **hide the WhatsApp action when there is no
   template** — `useWhatsAppSend` exposes `hasTemplate` (false ⇒ `WhatsAppAction` and
   `CardWhatsAppFooter` render nothing for that order). `OrderCreatedModal` is unaffected (post-create
   status is always Booked).
5. **Pickup window seam** — `buildMessage` / `whatsappUrl` accept an optional `pickupWindow`; when
   absent they use the fallback **"during our working hours"**. (29.8 supplies the real value.)

## Scope (out)

- Working-hours data, Settings UI, real pickup-window derivation (29.8).
- Delay, payment reminders, `action_key` logging (future).

## Files

- Rewrite: `frontend/src/lib/whatsappTemplates.ts`.
- Modified: `frontend/src/lib/useWhatsAppSend.ts` (expose `hasTemplate`),
  `frontend/src/components/orders/OrderDetailDrawer/WhatsAppAction.tsx` and
  `frontend/src/components/dashboard/CardWhatsAppFooter.tsx` (hide when `!hasTemplate`).

## Review (how to verify)

- `npm run type-check` clean.
- Each status sends its finalized copy with the correct payment line (Booked/Ready/Delivered) and
  none for `unbilled` / Delivered-paid.
- A **Partial Delivery** order shows **no** WhatsApp action on the detail Overview and **no** card
  footer.
- Pickup window reads "during our working hours" (fallback) until 29.8.

## Done when

All surfaces use the finalized warm templates with status-aware payment context, `{item}`="order",
Partial Delivery hides the action, and the pickup window falls back cleanly pending 29.8.
