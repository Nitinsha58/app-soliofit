# VS-29.1 — Backend: Order Message Tracking

**Program:** [VS-29 overview](./00-overview.md) · **Layer:** Backend (`apps/orders`) · **Status:** Pending
**ADR:** [ADR-0010](../../adr/ADR-0010-whatsapp-click-to-chat-messaging.md) §4, §5

Persist that a status message was sent for an order so the UI can show a "sent" state and
support resend. Additive and **non-breaking** — no existing endpoint, field, or migration
behavior changes.

## Scope (in)

1. **Model `OrderMessageLog`** (`apps/orders/models.py`) — append-only send log, mirroring
   the `OrderActivity` conventions (UUID PK, `TextChoices`, `db_table`, `metadata` JSON):

   | Field | Type | Notes |
   |-------|------|-------|
   | `id` | UUIDField PK | `default=uuid.uuid4`, non-editable |
   | `order` | FK → `Order` | `on_delete=CASCADE`, `related_name='message_logs'` |
   | `order_status` | CharField(`Order.Status.choices`) | the status the message announced |
   | `channel` | CharField(`Channel.choices`, default `whatsapp`) | `Channel` TextChoices (`whatsapp`) — room for sms/email later |
   | `template_key` | CharField | which predefined template was used (audit + future template mgmt) |
   | `sent_by` | FK → `users.User` | `on_delete=SET_NULL, null=True, blank=True` (attribution only) |
   | `sent_at` | DateTimeField | `auto_now_add=True` |
   | `metadata` | JSONField | `default=dict` — e.g. normalized phone, payment-block flag, message snapshot |

   `Meta`: `db_table='order_message_logs'`, `ordering=['-sent_at']`,
   index on `(order, order_status)`. Tenancy follows the order (scope via `order.boutique`,
   like `OrderActivity` — no denormalized boutique FK).

2. **Endpoint `POST /api/orders/{id}/messages/`** — `OrderViewSet` detail `@action`
   (`detail=True`, `methods=['post']`, url_path `messages`). Body
   `{ order_status, channel?='whatsapp', template_key, metadata? }`. Validates the order
   belongs to the caller's boutique (`self.get_object()`), `order_status` ∈
   `Order.Status`, creates one `OrderMessageLog` row with `sent_by=request.user`. Returns
   **201** with the created log (or the refreshed order detail incl. `messages_sent`).
   Re-sending the same status is allowed (appends a new row).

3. **Derived `messages_sent` on the order DETAIL serializer only** — a
   `SerializerMethodField` returning `{ <status>: <latest sent_at ISO> }` (latest row per
   `order_status` for that order). **Not** added to the list/board serializer (avoids N+1;
   the button only exists on the detail Overview). Prefetch `message_logs` on the detail
   `get_queryset`/`get_object` path.

4. **Migration** — one additive migration creating `order_message_logs` + its index.

## Scope (out)

- No frontend (29.2). No template content lives here (only `template_key` is stored).
- No automated sending, no Business API, no delivery/read receipts (ADR-0010 §5; §2.5 Post-MVP).
- No board/list serializer change.

## Files

- Modified: `apps/orders/models.py` (add `OrderMessageLog`), `apps/orders/serializers.py`
  (detail serializer `messages_sent` + a thin `OrderMessageLog` serializer),
  `apps/orders/views.py` (the `messages` action), `apps/orders/admin.py` (register, optional).
- New: `apps/orders/migrations/00XX_ordermessagelog.py`.

## Review (how to verify)

- Migrate in Docker: `docker compose -f docker-compose.dev.yml exec backend python manage.py migrate`.
- `POST /api/orders/{id}/messages/` with `{order_status:"Ready", template_key:"status_ready"}`
  → 201; `GET /api/orders/{id}/` now shows `messages_sent: {"Ready": "<iso>"}`.
- Second POST for `Ready` → another row; `messages_sent.Ready` reflects the latest timestamp.
- POST to an order outside the caller's boutique → 404/403; invalid `order_status` → 400.
- Confirm the board/list endpoints are unchanged (no `messages_sent`, no extra queries).
- Hand off to Nitin + automation testing tool.

## Done when

A status message send is recorded server-side and the order detail exposes a
`messages_sent` map, with no change to existing order/list/board behavior.
